# 视觉质检 Agent v2：从 CPU 原型到可验证的检测与学习系统

规划日期：2026-10-13。状态：**设计与待办，尚未实施**。v1 冻结为 `v1.0.0`；v2 以独立候选模型与实验报告推进，保持 v1 可运行、可回滚。首选仍为 Windows 本地 CPU 推理；训练时间较长的实验可选用 GPU，CPU 用户不因缺少 GPU 而失去基础功能。

## 1. v2 要解决的实际问题

v1 已完成闭环，但检测器使用手工颜色与纹理特征，且将图像压成 96×96。KolektorSDD2 主检测 Image AUROC 为 0.928229，不能说明接近阈值的缺陷都能被识别。独立路由验收出现 1/73 缺陷被放行，95% 漏检上界 6.33%；服务因此关闭自动放行，测试集人工复核率 80.58%。

v2 的核心交付是：让正式深度检测器进入同一套服务与校准流程；保留细小缺陷；让缺陷反馈能够训练一个有监督的二级模型；用冻结的整条策略和独立数据证明收益。VLM 描述、更多页面和 GPU 部署不作为优先成功标准。

| 维度 | v1 已有证据 | v2 目标与验收方式 |
|---|---|---|
| 检测能力 | KSDD2 AUROC 0.928229 | 研究目标 ≥0.96；先在开发数据选择配置，再固定配置报告官方测试。未达到时保留负结果 |
| 微小缺陷 | 96×96 指标，小区域可能消失 | 保持纵横比、可选切片；原图尺寸评估；按缺陷面积区间报告召回与区域定位 |
| 业务风险 | 1/73 漏检，上界 6.33%，不放行 | 冻结完整策略后，独立验收上界 ≤1% 才允许放行；样本不够即保留关闭状态 |
| 人工成本 | 测试复核率 80.58%，放行 0% | 有条件目标：通过相同风险验收后，复核率相对 v1 降低 ≥25%（相同基率时约 ≤60.43%），同时约束正常自动误报率 ≤10% |
| 主动学习 | 合成集 oracle 仿真；缺陷标签不训练检测器 | 真实数据 3 个种子，比较相同成本下随机/不确定性/多样性策略；目标为达到同一预注册性能时少用 ≥20% 标注成本，不保证必然优于随机 |
| CPU 性能 | 轻量检测器 p95 3.65 ms，不含 HTTP | 深度候选目标：固定硬件、线程数和图像尺寸，batch=1 HTTP 端到端 p95 ≤250 ms；实测前属于预算目标 |
| 可复现性 | 本机脚本与汇总结果 | 配置、权重来源及哈希、环境锁定、划分指纹、逐图预测、失败样例、三种子统计、CI 与版本回滚 |

80.58% 来自 KSDD2 的测试缺陷基率，不能直接当作产线成本。v2 同时报告原始测试比例和按 0.1%、1%、5% 缺陷基率重加权的结果：`review(π)=(1−π)·P(review|normal)+π·P(review|defect)`。这仍依赖类条件分布稳定的假设。

v1 的官方测试结果已经被查看，后续 v2 对同一测试集的比较必须披露为持续基准比较，不能重新称作从未见过的最终测试。任何上线风险结论仍来自新的独立验收数据。

## 2. 优先级与范围

### P0：先具备可靠的模型替换和风险验收

1. **统一模型适配器。** 定义 `Detector.fit / predict / export / metadata`。固定输出 `image_score`、原图坐标系 `anomaly_map`、选样用 `embedding` 和分阶段耗时；固定分数越大越异常。实现 v1、正式 PatchCore、EfficientAD 三个后端，校准与队列不再依赖 `PatchMemory` 的内部字段。
2. **统一推理契约。** 模型包显式保存输入尺寸、RGB 顺序、归一化、保持比例方式、切片及合并规则、分数聚合方法和热力图插值。测试灰度/RGBA、非方图、正常与异常、多尺寸输入。不能给新后端复用 v1 的分数阈值。
3. **小缺陷处理。** 先比较等比例缩放到 256/384 与 256 切片、25% 重叠；以真实尺寸和内存预算调整。整图和切片的分数聚合在开发集确定。切片不作为独立校准或验收样本；同一工件及其切片、增强必须同组。
4. **独立验收记录。** 每个候选保存完整策略哈希、校准集指纹、验收集指纹、缺陷数、漏检数、风险上界、适用类别与分布说明。缺失、过期或不匹配的证书导致自动放行关闭。

首先完成 PatchCore；EfficientAD 作为精度/时延对照。PatchCore 使用预训练特征与记忆库，无需反向传播优化；这不意味着特征提取和近邻搜索在 CPU 上免费。正式实现与导出接口依据 [Anomalib PatchCore 文档](https://anomalib.readthedocs.io/en/v2.0.0/markdown/guides/reference/models/image/patchcore.html)，实施时选择已验证版本并锁定，避免只写宽泛 `>=` 范围。EfficientAD 的训练资源、归一化统计和可能使用的外部数据单独记录，参考 [原论文](https://arxiv.org/abs/2303.14535)。

### P1：证明二级复核和反馈学习有价值

1. **二级监督分割。** 优先小型 U-Net，图像标签预算与像素标注预算分开计费；使用原训练/标注池的缺陷掩膜。比较一级单独、一级+二级、同预算监督模型三组，公开二级调用比例与总延迟。
2. **固定整条级联策略。** 二级模型只接收一级不确定样本，但完整系统的放行漏检在独立验收集全部缺陷上计算。不能把第二级各自的覆盖保证直接当作级联保证。可让第二级先仅给人工建议，再在新验收通过后允许它自动决策。
3. **真实主动学习。** 选样策略包含随机、不确定性、多样性，以及“不确定性+多样性”混合；不能只从已确认缺陷中挑选。保留随机抽检支路用于观察非不确定区域，记录入选概率、样本来源和标注耗时，区分主动采样集与代表性评估集。
4. **缺陷标签有明确用途。** 正常反馈更新单类记忆库，缺陷反馈训练二级分割器；不把缺陷塞入正常记忆库。候选训练失败不影响服务中的模型。标签冲突、纠正与标注规范版本纳入审计。

### P2：演示完整度与生产适配

- 特征空间漂移监测、按类别/批次统计看板、批量推理与导出错误案例。
- 模型注册表、影子评估、显式提升与回滚；首次实现保留单机部署。
- VLM 生成缺陷描述与复核提示，只引用图像证据并记录模型版本；不生成真值、不改变自动放行。
- 真实相机、Jetson、GPU、LOCO 专用逻辑异常路径放在后续扩展，不挤占 P0/P1 验证时间。

## 3. 数据设计：两条评测路径

**A. 官方检测基准。** KSDD2 做全量基线复现；先选 MVTec AD 的 bottle/cable/capsule 与 VisA 的 pcb1/pcb2 开发适配，所有配置冻结后再扩展 MVTec 15 类、VisA 12 类。BTAD 和 LOCO 作为扩展。不同类别先分别计算 AUROC 再宏平均，不能直接混合未校准的分数。

正常图无 mask 时补零；缺陷 mask 缺失时报告缺失数量。定位基于恢复到原图尺寸的预测热力图和原始掩膜；按统一区域连通与积分实现报告 AUPRO。LOCO 正式结果使用其专用 sPRO，不拿普通 PRO 替代。

**B. 路由、主动学习与风险研究。** 只从官方训练部分和新增独立采样建立 `train / dev / prob_fit / pool / calibration / acceptance`。现有 v1 的 `validation` 在新 schema 中映射为一次性 `acceptance`，另加 `dev`，避免把调参验证和风险验收混为一谈。官方 `test` 始终保留。没有训练缺陷的数据集只报告排序与正常误报控制；不能偷用其测试异常来造出路由能力。

KSDD2 官方训练有 246 个缺陷：若再分给监督训练、校准和验收，无法仅靠这个训练集完成 1% / 95% 的正式验收。**这是样本限制，不能靠重复增强、切片或多次随机划分增加独立证据。** 最小规划为同一目标类别 ≥99 个独立缺陷用于 1% conformal 的离散分辨率，另有 ≥299 个独立缺陷用于零漏检时的单次 95% 风险验收；监督训练、开发、概率拟合用到的缺陷不计入这两份。99/299 是数学下限，不是保证一定通过的采样建议；出现漏检需更大样本量。

正式验收数据建议按时间/工件/批次留出。若源数据没有这些信息，明确说明无法验证物理独立性。不得简单把不同产品缺陷混成 299 个后声称每类都达标。新增数据来源优先是具有合适元数据和许可的公开数据；真实产线校准仍需要目标产线代表性数据，自采不是检测主基准的前提。

## 4. 校准、选模与验收规则

1. 预先写定目标 FNR=1%、置信度=95%、误报成本、候选预算和上线规则。概率校准拟合在 `prob_fit`；路由曲线/超参数选择在 `dev`；conformal 在独立 `calibration`。
2. 在访问 `acceptance` 标签前，冻结检测器、预处理、切片合并、二级模型、漂移规则和阈值。报告冻结策略哈希。
3. 同时记录原始模型分数、未经验收限制的路由、实际服务路由。避免因关闭放行得到零漏检就宣传通过目标。
4. 使用缺陷级独立样本计算 Clopper–Pearson 单侧上界。多候选反复验收需要新的留出集或预先定义的多重检验/序贯方法；v2 首选简单的一次性最终验收。
5. 模型更新后，重新获取未参与选样或候选筛选的独立校准与验收数据。离线主动学习可以复用开发评价集画曲线，但明确它不是生产风险证书。
6. 漂移触发后进入复核并开启调查；不得自行调整阈值后继续沿用旧证书。人工错误率由双人复核样本估计，不假设人工绝对正确。

## 5. 主动学习实验的公平性

- 固定 3 个种子 `17 / 42 / 2026`，所有策略从相同初始训练集与相同 pool 开始；预算从 `10 / 20 / 40 / 80 / 160` 中选择实际 pool 支持的点。
- 初始训练、缺陷掩膜、概率校准、conformal、验收分别计入标签总成本；不能只报迭代新增量。
- 记录每轮 acquisition 的模型版本、分数、嵌入、选中 ID、随后揭示的标签、掩膜时间、训练时间。先选择再读 oracle 真值。
- 先做固定 pool 仿真，再模拟新缺陷/新类别和按时间漂移；新类别从未进入源模型训练。相同工件不跨集合。
- 报告预算—性能、预算—复核率、被发现的缺陷数，以及达到目标的总标签数。没有达到目标时记为 `not_reached`，不能把最大预算当作成功。
- 比较均值和离散程度，图像 AUROC 差异可做按工件/组的配对 bootstrap；3 个种子不是 3 份独立产线数据，不能夸大置信结论。

## 6. 工程接口与模型生命周期

建议目录按职责扩展，不立即改写 v1 全部代码：

```text
src/vision_qc/detectors/       协议、v1、PatchCore、EfficientAD、ONNX 适配器
src/vision_qc/preprocessing/  等比例缩放、切片、坐标还原
src/vision_qc/routing/        一级/二级策略、校准与风险验收
src/vision_qc/registry/       模型包、校验、状态转换及回滚
configs/v2/                  数据、模型、预算和实验配置
scripts/run_matrix.py        固定配置批量实验
results/v2/                  汇总指标与报告，不提交原始图像或本机路径
```

模型包保存 schema 版本、后端、输入输出契约、权重 SHA-256、数据指纹、代码 commit、环境、校准参数和验收记录。生命周期为 `candidate → calibrated → evaluated → approved → active`；验收不通过留在 `evaluated`，漂移可进入 `suspended`。服务加载前检查 schema、哈希和类别。新模型不可覆盖旧目录。

推理 API 保留 v1 字段，追加阶段耗时和可选二级结果；后台训练采用任务 ID、进度、失败原因与取消状态，避免占用请求线程。初版使用 SQLite 单机队列即可，只有压测证据表明需要才引入 Redis/PostgreSQL。

ONNX 在固定样本集上对比原模型分数、热力图和最终路由。容差需按模型尺度登记，并检查阈值附近的路由翻转，不能只有均值误差。后端切换若改变评分函数，重新校准与验收。图像导入、像素定位、校准集合及证书拒绝逻辑都需有针对性测试。

性能报告分别给出图像解码、预处理、一级、二级、路由、存储、HTTP 总时间；预热后至少 200 次，batch=1，记录线程数、CPU型号、输入尺寸与切片数，报告 p50/p95、吞吐、峰值 RSS 和模型大小。多线程、并发或量化只在相同准确性与路由检查通过后比较。

## 7. 实施里程碑与交付

以下是单人工作量估计，依赖下载、CPU 训练速度和数据可用性，不是交付日期承诺。

| 里程碑 | 优先级 / 预计工作量 | 可审查成果 | 退出标准 |
|---|---|---|---|
| M0 复现与环境 | P0 / 1–2 天 | CPU 深度模型独立环境、依赖锁、v1 回归、数据指纹 | 全新环境跑通 v1；依赖来源和数据协议明确 |
| M1 正式模型接入 | P0 / 3–5 天 | PatchCore 适配器、训练/服务/ONNX、EfficientAD 对照 | 真实图经 API 得到分数和定位；三后端契约测试通过 |
| M2 定位与模型选择 | P0 / 3–4 天 | 等比例/切片对照、原图定位、错误样例报告 | 在开发集完成预注册配置选择；官方测试报告分辨率与统计 |
| M3 路由与验收 | P0 / 2–4 天，数据采集另计 | schema 升级、完整策略哈希、候选风险报告 | 证据足则验收；不足则明确缺口且保持放行关闭 |
| M4 反馈与二级模型 | P1 / 4–6 天 | U-Net、三种子真实 AL、成本曲线、级联对照 | 不泄漏官方测试；缺陷反馈有实测训练用途；正/负结果均保留 |
| M5 交付与回滚 | P1 / 2–3 天 | 版本注册、一次升级/回滚、性能和 Docker 检查 | 新电脑可复现；报告已知限制；所有 P0 检查可执行 |

估计 15–24 个有效工作日；GPU、额外数据和生产验收等待时间另计。若只做 CPU 最小加强版，先交付 M0–M3，主动学习收益与二级分割延后，不把它们写进已完成列表。
